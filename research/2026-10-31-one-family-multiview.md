# Plan B — one-family multiview feasibility, Build 40 brightness, and DuoView Mono comparison

Date: 2026-10-31. **Research only. No C++ source, build workflow, binary, or runtime configuration was changed.** Target: S.T.A.L.K.E.R. 2 / UE5.5 / DX12 / OpenXR. Companion document: [Build 51 mapping](./2026-10-31-build51-map-for-3view.md).

**[SOURCE-READ — conclusion]** A three-view single `FSceneViewFamily` with three `eSSP_FULL` cameras and independent `FSceneViewStateInterface` instances is **structurally possible in UE's general multiview/split-screen interface**. **It is NOT a demonstrated viable UE5.5 + Lumen + DLSS solution in STALKER 2.** Epic engineers document a **two-view hard limit for Lumen** (`LUMEN_MAX_VIEWS = 2` and a `Views.Num() > 2` rejection), independent of whether the additional views are `FULL`, `PRIMARY`, or `SECONDARY`. Epic documented this in [May/July 2025](https://forums.unrealengine.com/t/plans-for-lumen-3-4-split-screen-support/2580645/4) and [April 2026](https://forums.unrealengine.com/t/what-rendering-features-are-supported-in-splitscreen-with-multiple-views/2722648/2). The *exact STALKER 2 compiled UE5.5 Lumen branch and check* were not inspected here; verify with an RDG/GPU capture before equating the documented engine rule with an observed game result.

**[SOURCE-READ — recommendation]** If Lumen parity is a requirement, prefer **two view families per gameplay frame**: one family with the **two independently rendered eye foveae**, and a separate **one-view shared mono periphery**. This is still **three scene renders**, not four. It avoids any >2-views-per-family Lumen rejection, although it requires explicit history, render-target, ordering, composition, and resource-lifetime work. It is NOT a guaranteed performance or DLSS fix. Do not confuse `2 families` with `2 scene renders`.

## 2. Brightness: two *independent* mechanisms; root cause not proved

**[SOURCE-READ]** Mechanism **A — pass/history labeling**: UE explicitly distinguishes `eSSP_FULL` (not a stereo pass), `eSSP_PRIMARY` (own pass) and `eSSP_SECONDARY` (can be instanced), documented in [Epic's `StereoRendering.h` API](https://dev.epicgames.com/documentation/unreal-engine/API/Runtime/Engine/EStereoscopicPass). A secondary view may be paired with a primary for stereo treatment, and Epic exposes `FSceneView::GetPrimarySceneView()`, `GetSecondaryViews()`, `StereoPass`, `StereoViewIndex`, `State` and `bEyeAdaptationAllViewPixels` ([Epic `SceneView.h`](https://dev.epicgames.com/documentation/en-us/unreal-engine/API/Runtime/Engine/FSceneView)). **Inference:** forcing an extra independently framed context/fovea to follow a stereo-secondary view path can produce non-matching exposure, temporal, or lighting behavior. **UNVERIFIED:** which exact exposure/Lumen code was taken for Build 40's four slots, or whether the visible brightness was a direct consequence of this mechanism.

**[SOURCE-READ]** There is a *project-specific controlled contrast*: Mono Stage 2–4 allows a **second** view in a **singleton native render family** to be temporarily relabeled `eSSP_PRIMARY` when `can_independent_shading` succeeds, then restores the init option after construction. See [`duoview/joey_stage1/apply_stage234.py#L653-L676`](https://github.com/liviutrn/UEVR-Quad-Views-Mono/blob/7486fc59890b14673cd50770b0dafeb692576716/duoview/joey_stage1/apply_stage234.py#L653-L676). The guard demands **`views->count == 1`**; this must **not** be represented as something already active in Build 40's simultaneous four-view family.

**[SOURCE-READ]** Mechanism **B — Lumen view-count hard stop**: UE engine representatives state `LUMEN_MAX_VIEWS=2` and `ShouldRenderLumenForViewFamily()` disables Lumen when `Views.Num()>2` (except cube capture); [2026 Epic response](https://forums.unrealengine.com/t/what-rendering-features-are-supported-in-splitscreen-with-multiple-views/2722648/2), [2025 Epic response](https://forums.unrealengine.com/t/best-practice-for-lumen-and-non-lumen-lighting-setups-in-the-same-scene/2647830/5). This applies to **four as well as three** simultaneous views, *regardless of pass labels*. **Inference:** it can produce a major apparent lighting/brightness difference versus two-view Native Fix. But if *only* certain Build 40 slots were bright while others retained Lumen, **one global family cutoff alone cannot explain that asymmetry**; verify which family UE actually rendered for each slot.

**[SOURCE-READ — diagnosis status]** **No file:line evidence proves the exact root of the reported brightness.** What the source proves is: (1) Build 40 disabled the already known shading-relabeled Native Fix, (2) four views were retained together, and (3) the relevant engine has a documented Lumen family-count hazard. Claiming that either one alone *caused* the observed output would exceed the evidence. The missing discriminators are runtime pass labels, `PreExposure`/`GetLastEyeAdaptationExposure`, GI/reflections enablement and per-slot GPU/RDG pass activity.

**[SOURCE-READ — suggested A/B diagnosis, NOT EXECUTED]** First preserve an exact in-game camera position, fixed weather and lighting, disable dynamic eye adaptation *only for a diagnostic run*, compare a 1-view and 2-view family with a 3-view/4-view family, and record `View.StereoPass`, `State`, `PreExposure`, post-process exposure compensation, Lumen pass existence, and screenshot linear luminance. Re-run with pass relabeling *only*, then with family partitioning *only*. Do not treat gamma adjustment or tone-map output brightness as proof that GI is restored.

## 3. Can UE5.5 hold three `FULL` views in one family?

**[SOURCE-READ]** **Structural API: YES.** `FSceneViewFamily` is a set of views into one scene; it has a `Views` array, shared `Scene`, `RenderTarget`, `EngineShowFlags`, and family-level screen percentage configuration. `FSceneView` has its own state pointer, view matrices, and view rectangles. Unreal's split-screen path is precedent for multiple `eSSP_FULL` views in one family. See [Epic `FSceneViewFamily`](https://dev.epicgames.com/documentation/en-us/unreal-engine/API/Runtime/Engine/FSceneViewFamily), [Epic `FSceneView`](https://dev.epicgames.com/documentation/en-us/unreal-engine/API/Runtime/Engine/FSceneView), and [Epic `EStereoscopicPass`](https://dev.epicgames.com/documentation/unreal-engine/API/Runtime/Engine/EStereoscopicPass). **One shared target** still requires disjoint, valid view rectangles, appropriate clears and screen-pass viewport handling; this is not equivalent to three independent same-sized targets.

**[SOURCE-READ]** **Lumen: NO, not by default.** The documented three-view cutoff is a showstopper for the requested combination. Epic indicated that raising `LUMEN_MAX_VIEWS` in engine source might unlock more views, but with severe performance cost and possible additional fixed-two-view assumptions ([Epic support, May 2025](https://forums.unrealengine.com/t/plans-for-lumen-3-4-split-screen-support/2580645/4)). This is not a realistic simple runtime UEVR hook for a closed shipped game. **UNVERIFIED:** whether S.T.A.L.K.E.R. 2's modified 5.5 engine adds an exemption.

**[SOURCE-READ]** **DLSS: UNVERIFIED.** NVIDIA publishes a UE5.5 DLSS plugin, but public product availability is not evidence of support for 3 unrelated subrects/histories in one family ([NVIDIA DLSS](https://developer.nvidia.com/rtx/dlss)). Three `FULL` views might receive a family-level temporal upscaler, yet one cannot infer independent NGX feature/context histories or correct per-view jitter, motion vectors, reset behavior and resolution changes from the UE `FULL` label. Require an actual STALKER2 UE5.5 DLSS path trace and compare per-view `NGX` calls/feature handles. **UNVERIFIED:** whether the game's DLSS integration chooses an unsupported first-view-only path.

**[SOURCE-READ — important design correction]** Requesting **independent exposure for each view** is not automatically an improvement. It helps cameras behave independently in conventional split screen, but the two foveae and the shared periphery will be composited into the same retinal scene. Different metering regions can produce bright rings/feather seams. Keep **independent temporal view states** while enforcing **one coherent final exposure/pre-exposure policy**, or prove equal exposure via instrumentation.

## 5. Smallest honest change from Build 40

**[SOURCE-READ — minimal *experiment*, not proven fix]** Change only **the new view's constructor pass label** to an independent pass (`eSSP_PRIMARY` where safely supported by native singleton fix, or `eSSP_FULL` for split-screen-style views), preserving the original cameras, state pointers, rectangles, resources, and composite. Measure exposure and Lumen against unmodified Build 40. The existing guarded secondary→primary recipe in [`apply_stage234.py#L653-L676`](https://github.com/liviutrn/UEVR-Quad-Views-Mono/blob/7486fc59890b14673cd50770b0dafeb692576716/duoview/joey_stage1/apply_stage234.py#L653-L676) is the *closest known project-side mechanism*, but it is written for a **singleton family**. Blindly removing its `views->count==1` guard is not justified. **UNVERIFIED** that simply relabeling Build 40's four simultaneous views will cure brightness.

**[SOURCE-READ — smallest *Lumen-correct architectural* change]** **Partition before the renderer sees 3+ views.** Keep the same three real cameras and render rectangles and most of Build 40's producer/compositor contracts, but submit **two eye foveae in a <=2-view family** and **one shared context in a 1-view family**. This mimics the family-count invariant that the two-view Native Fix already avoids violating. Exactly how producer targets and renderer histories are owned must be reworked and tested; no promise of a trivial patch. If the actual game cannot run DLSS for the split-screen pair, use **three singleton submissions** as the fallback (three full renders in separate <=2-view families) and measure their overhead.

**[SOURCE-READ — scope/priority]** Do **not** spend implementation time on changing all four views to `FULL` in one family as a definitive Plan B. Even if exposure parity improves, the known Lumen count limit remains. The architectural go/no-go is a **2+1 family** proof with Lumen+DLSS, **before** resizing per-view render targets or tuning performance.

## 6. Proposed proof / acceptance measurements (all UNEXECUTED)

**[SOURCE-READ — experimental proposal]** Add logging **only in a future, explicitly approved implementation step**; no source edits were made for this report. **[SOURCE-READ — experimental proposal]** A/B four deterministic cases in STALKER 2 at identical camera/weather/time with no mods influencing lighting: **A:** native two-view shading-fix baseline; **B:** Build 40 four views unchanged; **C:** three `FULL` in one family; **D:** two foveae family + one mono context family. ## 7. Adversarial review / limitations

**[SOURCE-READ — review]** This report does **not** claim to have read the Epic-licensed UE5.5 source code or the full injected Joey `FFakeStereoRenderingHook.cpp` compilation unit; its file:line evidence for Build 40 is from **pinned Python overlay text**, workflow, and contract headers.
