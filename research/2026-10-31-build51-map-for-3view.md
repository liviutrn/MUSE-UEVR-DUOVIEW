## 1. Target extents, construction, format, equal-size assumptions

### Dimension origin and one-target-per-slot construction

**[SOURCE-VERIFIED]** The chain is:

1. `VR::quadview_begin_draw`'s injected block obtains `width=get_hmd_width()`, `height=get_hmd_height()` in [`quadview/apply_quadviews.py#L380-L405`](https://github.com/liviutrn/UEVR-Quad-Views-Mono/blob/f4e086cde6d4a183cf2c1223dd9effaf6f8f7a77/quadview/apply_quadviews.py#L380-L405).
2. `uevr::quadview::make_layout(width,height, crop_width,crop_height,context_scale,foveal_density,focus)` is invoked in [`apply_quadviews.py#L475-L500`](https://github.com/liviutrn/UEVR-Quad-Views-Mono/blob/f4e086cde6d4a183cf2c1223dd9effaf6f8f7a77/quadview/apply_quadviews.py#L475-L500). [`QuadViewGeometry.hpp#L63-L106`](https://github.com/liviutrn/UEVR-Quad-Views-Mono/blob/f4e086cde6d4a183cf2c1223dd9effaf6f8f7a77/quadview/QuadViewGeometry.hpp#L63-L106) specifies `atlas_width = eye_width*2`, `atlas_height = eye_height`. Context rect: `round(eye_width*context_scale) × round(eye_height*context_scale)`; focus rect: `round(eye_width*crop_width*focus_density) × round(eye_height*crop_height*focus_density)`. The two source rectangles for each eye are **offset into the corresponding atlas half**.
3. The caller explicitly passes **atlas**, not rect, dimensions to `rtm->ensure_quadview_native_target_set(layout->atlas_width,layout->atlas_height)` in [`apply_quadviews.py#L505-L512`](https://github.com/liviutrn/UEVR-Quad-Views-Mono/blob/f4e086cde6d4a183cf2c1223dd9effaf6f8f7a77/quadview/apply_quadviews.py#L505-L512).
4. In `VRRenderTargetManager_Base::ensure_quadview_native_target_set`, injected via [`apply_quadviews.py#L746-L920`](https://github.com/liviutrn/UEVR-Quad-Views-Mono/blob/f4e086cde6d4a183cf2c1223dd9effaf6f8f7a77/quadview/apply_quadviews.py#L746-L920), `build->width=width; build->height=height` is set once, then a four-iteration loop calls `kismet->create_render_target_2d(world,width,height,2,clear_color,false)` four times (lines 794–816). It validates each resource chain with the same `build->width/height`, and stores the same extent in each source snapshot. This uses **four separate 2D render targets**, not four slices of one texture array.
5. `apply_quadview_target_lifetime.py` [lines 18–66 and 90–135](https://github.com/liviutrn/UEVR-Quad-Views-Mono/blob/f4e086cde6d4a183cf2c1223dd9effaf6f8f7a77/quadview/apply_quadview_target_lifetime.py#L18-L135) replaces owner lifetime behavior: for **each source**, spawn a UE `AActor` through `UGameplayStatics::spawn_actor`, add a `USceneCaptureComponent2D`, turn off `bCaptureEveryFrame` and `bCaptureOnMovement`, set component visibility false, create the same Kismet 2D texture, and store it in the component's `TextureTarget` property. These components **retain the textures**; they are not the active source render loop. Retire/revalidate on the game thread. It is therefore incorrect to describe Build 51 as merely four independently rooted temporary textures.

**[SOURCE-VERIFIED]** The `2` format argument is the UE `ETextureRenderTargetFormat::RTF_RGBA8` enum value (not `RTF_RGBA8_SRGB`). See [Epic UE 5.5 enum](https://dev.epicgames.com/documentation/unreal-engine/API/Runtime/Engine/Engine/ETextureRenderTargetFormat?application_version=5.5) and [Kismet 2D target API](https://dev.epicgames.com/documentation/en-us/unreal-engine/API/Runtime/Engine/UKismetRenderingLibrary). **[MEASURED—USER-REPORTED]** `6984×2776` was reported in the prompt's log. It corresponds to `3492×2776` per HMD eye with this `2W×H` layout; that HMD size is an inference from the reported number, not a new HMD measurement.

**[ESTIMATED]** To right-size safely: represent a physical `TargetDesc{width,height,format}` **per role**; retain a **logical** full-FOV crop/projection and independently map it to an **output** `(0,0,w,h)` view rectangle; ensure view-state, history, UV, texture-space coordinate, and shader constants consistently distinguish logical vs physical rectangles. Rework target validation, producer rect lookup, native renderer singleton dispatch and compositor sampling together. The *first* 3-view correctness build should **not** simultaneously attempt this refactor.

**[ESTIMATED—COLOR RT ONLY]** Four `6984×2776×4 bytes` RGBA8 targets total ~`310,201,344 bytes = 296 MiB` of raw color-resource payload (excluding row padding, mips, RHI metadata, residency, scene textures). At default `crop=0.5`, `density=1` and `context=0.2`, the theoretical 3-view local sizes are approximately `698×555` for one shared context and `1746×1388` for each focus, or roughly **20 MiB** raw color payload. This estimates VRAM, **not** raster GPU time, GBuffer sizes, Lumen cost, or DLSS resource allocation.

## 2. Scene textures: family target or view rectangle?

**[SOURCE-VERIFIED]** The Build 51 **hook** intercepts the renderer boundary and, via [`QuadViewFamilyRouting.hpp::dispatch_main_views`](https://github.com/liviutrn/UEVR-Quad-Views-Mono/blob/f4e086cde6d4a183cf2c1223dd9effaf6f8f7a77/quadview/QuadViewFamilyRouting.hpp#L267-L297) plus [`apply_quadview_native_delivery.py`](https://github.com/liviutrn/UEVR-Quad-Views-Mono/blob/f4e086cde6d4a183cf2c1223dd9effaf6f8f7a77/quadview/apply_quadview_native_delivery.py#L241-L275), changes the *same* `FSceneViewFamily` to contain **one selected `FSceneView`** and switches `FSceneViewFamily::RenderTarget` to that source's `sdk::FRenderTarget*` before each actual `m_render_module_begin_render_viewfamily_hook.unsafe_call`. The first call can preserve the original family batch to service auxiliary families. `FFakeStereoRenderingHook::begin_render_viewfamily` briefly restores the four original views for GT source registration; the singleton is restored before UE copies it into its renderer [`apply_quadview_native_delivery.py#L277-L355`](https://github.com/liviutrn/UEVR-Quad-Views-Mono/blob/f4e086cde6d4a183cf2c1223dd9effaf6f8f7a77/quadview/apply_quadview_native_delivery.py#L277-L355).

**[SOURCE-VERIFIED]** UE distinguishes its scene texture extent from the sub-view rectangle. Epic's `FSceneTexturesConfig::Extent` is explicitly the extent of **all full-resolution scene textures**, not an individual view rectangle ([Epic FSceneTexturesConfig](https://dev.epicgames.com/documentation/unreal-engine/API/Runtime/Engine/FSceneTexturesConfig)); UE describes `FScreenPassTextureViewport` as a rectangle within a texture extent ([Epic Renderer API](https://dev.epicgames.com/documentation/unreal-engine/API/Runtime/Renderer)); `FSceneViewFamily` exposes `RenderTarget`, `Views` and family-level screen percentage and show flags ([Epic family API](https://dev.epicgames.com/documentation/en-us/unreal-engine/API/Runtime/Engine/FSceneViewFamily)). A separate UE 5.4 code excerpt names `FSceneRenderer::GetDesiredInternalBufferSize(ViewFamily)` and `PrepareViewRectsForRendering` ([SceneRendering.cpp call-site excerpt](https://indxzero.github.io/ue544cvarwiki/articles/r.test.viewrectoffset/index.html)). These establish that **view rect ≠ texture extent** and UE has a family-level internal-buffer-size path.

**[ESTIMATED / NOT VERIFIED FOR STALKER 2 UE5.5]** The exact `FSceneTexturesConfig::Extent` **for each native singleton callback** was **not** captured, so it is *not verified* whether the GBuffer in the game is `6984×2776`, a family/view-derived smaller extent, a pooled/preallocated extent, or a rounded maximum. UE generally allocates shared full-resolution scene textures from a renderer/family configuration, with per-view rectangles controlling active raster regions; **both may matter**. The patched family source target makes a full-atlas family extent plausible, **not proven**. Lumen uses several different screen-space, history, cache and resolution policies. DLSS engine integration creates/evaluates its own resources and may depend on view rect, output size, screen percentage, and NGX/DLSS path; neither can be assigned one uniform size from this hook alone. A log reporting the four **color** resources' extents is **not evidence** of GBuffer/Lumen/DLSS extent.

**[ESTIMATED — required discriminating test]** Capture *one complete Build 51 frame* with a GPU capture / UE RDG diagnostic, annotate all four singleton render callbacks, and record for **each**: `FSceneViewFamily::RenderTarget->GetSizeXY()`, `Views.Num()`, `FSceneView::ViewRect`, `UnscaledViewRect`, `FSceneTexturesConfig::Extent` (when accessible), D3D12 descriptors of GBuffer A/B/C, scene color/depth, SSR/AO, Lumen downsample/intermediate/history textures, DLSS input depth/motion vectors/color and NGX output. Compare after changing only context scale with constant HMD size. **If color target extent remains fixed and GBuffer extent remains fixed, target right-sizing is mainly memory; if GBuffer or DLSS work scales, measure GPU pass time to confirm actual savings.** No claim of per-target performance gain until this capture exists.

## 3. Context-only lower-quality settings: real hook, scope, risks

**[SOURCE-VERIFIED]** The actionable injection point is the **per-role dispatcher**, *after* `mutation.select_single(view[slot],target[slot])` and *before* the corresponding render-module call: [`QuadViewFamilyRouting.hpp::dispatch_main_views`](https://github.com/liviutrn/UEVR-Quad-Views-Mono/blob/f4e086cde6d4a183cf2c1223dd9effaf6f8f7a77/quadview/QuadViewFamilyRouting.hpp#L267-L297); patched into `FFakeStereoRenderingHook.cpp` by [`apply_quadview_native_delivery.py#L241-L275`](https://github.com/liviutrn/UEVR-Quad-Views-Mono/blob/f4e086cde6d4a183cf2c1223dd9effaf6f8f7a77/quadview/apply_quadview_native_delivery.py#L241-L275). The roles currently are `0 context-left, 1 context-right, 2 focus-left, 3 focus-right` ([`QuadViewGeometry.hpp#L25-L30`](https://github.com/liviutrn/UEVR-Quad-Views-Mono/blob/f4e086cde6d4a183cf2c1223dd9effaf6f8f7a77/quadview/QuadViewGeometry.hpp#L25-L30)). A 3-view architecture needs its own explicit `context` role and not a hardwired `view & 1` eye mapping.

**[ESTIMATED]** A safe customization is **not** to switch global CVar values between three calls. The singleton dispatch mutates a reused family, and game-thread/view construction, render-thread submission, feature setup and RHI tails can overlap. Changing global `r.Lumen.*`, `r.ScreenPercentage`, `r.NGX.*` or `r.SSR.*` in that window can contaminate the two focus renders and create temporal/pacing races.

| Control | Correct candidate scope | Assessment |
|---|---|---|
| Context raster resolution | Separate **context family** screen-percentage interface / per-view internal rect **before renderer snapshot**, retaining true full FOV | **[ESTIMATED]** Feasible with verified UE5.5 per-family API/SDK access; context rect already lower resolution, so extra screen percentage can double downsample and worsen quality |
| SSR, AO, fog and other show flags | Copy/apply per-context **`FSceneViewFamily::EngineShowFlags`**, before renderer construction, restore family state via RAII | **[ESTIMATED]** Technically plausible because UE exposes family show flags, but manipulating raw UE5.5 offsets in an injected title is unproven; postprocess/geometry feature decisions may be baked earlier |
| DLSS mode/preset and quality | Context-only per-family temporal-upscaler interface or game DLSS integration **before view family setup** | **[ESTIMATED]** High risk; mode is often integration/global rather than per call. Test **DLSS off / spatial** in context only first, preserving normal per-eye focus histories |
| Lumen GI/reflections quality | Only if verified per-family/per-view controls exist; otherwise leave both identical | **[ESTIMATED]** Avoid unsafe CVar flips and cross-view history reuse. Lumen has shared scene/global resources and persistent histories |
| Lighting/exposure parity | Consistent exposure/tonemapping/white balance; inspect seam against independently shaded focus | **[ESTIMATED]** Turning off AO/SSR/fog/Lumen in context can create visibly different ambient lighting and boundary seams. Cheapest is not automatically usable |

**[ESTIMATED—recommended sequence]** First preserve same quality and demonstrate 3 independent real render callbacks with three distinct scene states/targets. Then add a **single** context-only feature toggle (SSR or nonessential fog), with unchanged focus callback state and A/B images/timings. Only after this works try context-only upscaling/percentage. Do not begin with heterogeneous DLSS + Lumen + right-sized RTs: failures would be unassignable.
